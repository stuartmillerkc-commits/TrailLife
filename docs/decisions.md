# Build decisions

Where the build deliberately differs from `PLAN.md`, or settles something `PLAN.md` left open. **Where this file and `PLAN.md` disagree, this file wins.** Add a row whenever a phase makes a call like these.

## Phase 0 (2026-11-04)

| # | Topic | PLAN.md said | Decision | Why |
| --- | --- | --- | --- | --- |
| 1 | Unverified facts | §2, §6.2: an unsourced fact fails the build. CLAUDE.md: mark it `needsVerification` and keep going. | A fact needs a source and `verifiedOn` **unless** it has `"needsVerification": true`. Those print as warnings. `npm run check:strict` makes them errors; use it before an offline build for a meeting. | Lets a phase finish with honest gaps listed instead of guessed facts. |
| 2 | Battle positions | §8.7: grid squares like `"C4"` on an A–H × 6 grid. | Positions are `[x, y]` in the battle's field units (Cowpens: yards, 600 × 900). Grid squares are worked out from them. `battle.json` sets `field` and `grid`, and the check makes sure the grid tiles the field exactly. | The prototype needs coordinates for smooth movement and for its auto-generated sand table moves. One source of truth keeps the screen and the table in step. |
| 3 | Fog of war | §8.7: `knownToBritish` on each phase lists the units the British could see. | `hiddenFrom: { "<side>": [unit ids] }` on each phase lists the units that side *couldn't* see. | A "visible" list repeats almost every unit in every phase; a "hidden" list holds only the exceptions (at Cowpens, just Washington's cavalry). It also works for any side, not only the British. |
| 4 | Decision points | §8.7: `prompt` and `historicalOutcome`. | Also `side`, `who`, `choices`, `teaser` and `holdMapUntilReveal`. | These are all in the prototype. |
| 5 | Source registry | Ids like `csi-cowpens-staff-ride` are used, but nowhere says where they're defined. | `content/sources/sources.json`. A fact may cite a source inline (`source`) or by `sourceId`. Battles, phases, plans and what-ifs cite by id. | One place to fix a URL or a citation. |
| 6 | Patrol orders | §8.7: `patrolOrder.json` is one object. | `patrolOrder.json` is a list, and each order names its `side`. | So a battle can carry both commanders' orders (e.g. Tarleton's next to Morgan's). |
| 7 | Strategic layer | Not defined. | `battles/<id>/strategic.json` holds the regional map: bounds, places, rivers, borders and campaign arrows, all in latitude and longitude. | It holds the prototype's region-map data. |
| 8 | `terrain.json` | Listed in the §4 layout, but no format given. | Deferred to Phase 4a (illustrative contours) and 4f (baked USGS terrain). | It depends on the terrain pipeline. |
| 9 | Module activity types | §7.2: competition, discussion, hands-on, outdoor. | Also `presentation`, `guest` and `devotional`, plus `setting` (indoor, outdoor or either) for the filter. | The leader guide's opener, veteran Q&A and Armor of God don't fit the original four. |
| 10 | Battle phase order | The §11 table lists 4a, 4b, 4c, 4e, 4g, 4f, 4d; KICKOFF-PROMPTS.md lists them by letter. | Follow the §11 table: **4a → 4b → 4c → 4e → 4g → 4f → 4d**. | The capture the flag planner (4d) reuses game mode's dragging and arrows (4e), so 4e comes first. |
| 11 | Cowpens staff ride link | §8.3 links DTIC `ADA530379`; `sources/README.md` and the prototype link govinfo. | Use the govinfo copy. It's the one downloaded to `sources/cowpens-staff-ride.pdf`. | Verified download (208 pages). The DTIC id hasn't been checked. |
| 12 | Local server | §2 suggests `npx serve`. | `npm start` runs `scripts/serve.js`, which has no dependencies. | `npx` downloads a package the first time, so it fails offline. |
| 13 | Content list | Not covered. | `content/index.json` lists every content file. It's generated by `npm run index`, and `npm run check` fails if it's stale. | Browsers can't list a folder. |
| 14 | Schema checking | Not covered. | JSON Schema files live in `/schemas`, checked by `scripts/lib/json-schema-lite.js`, which has no dependencies. `schemas/schema-map.json` says which schema checks which file, and `.vscode/settings.json` mirrors it for live editor errors. | Nothing to install, and volunteers using VS Code see errors as they type. |
| 15 | Fonts | The prototype loads Google Fonts. | System fonts (Georgia or Segoe UI). The CSS still names the prototype fonts first, so they're used if installed. | Web fonts fail offline. |
| 16 | Repo root and history | — | Repo root is `military-heritage/`, connected to `stuartmillerkc-commits/TrailLife`. The original docs, prototype, printables and the Cowpens PDF went straight to `main`. Each phase then gets its own branch and pull request. | CLAUDE.md asks for one pull request per phase. |

## Phase 1 (2026-11-04)

| # | Topic | PLAN.md said | Decision | Why |
| --- | --- | --- | --- | --- |
| 17 | Prompts inside a module | §6.1: one `reveal` per module. | Modules may have `prompts`: items shown one at a time, each with its own answer (graduates, scenarios, discussion questions). → steps through them, then on to the next module; R reveals the current one. `promptLabel` names them ("Round 3 of 14"). | The academy sort and "Who can respond?" are a series of reveals. One reveal per module would show every answer at once. |
| 18 | Answer-key tables | §6.1: `reveal: { type: "table", factIds }`. | `reveal.table` holds `columns` and `rows`; each row cites `factIds`. `reveal.items` holds a list. `reveal.afterPrompt` says where the answer key appears among the prompts (0 = right after the opening screen; default: after the last). | A list of fact sentences can't fill a four-column answer key, and every cell still needs a source. |
| 19 | Projector content | §7.1: the display never shows leader notes or unrevealed answers. | One function, `src/presenter/display-snapshot.js`, builds everything the projector shows. It copies fields by name and fills the answer only after R. The display window loads no content files. Tests build every snapshot of every module and fail on any leaked string. | One gate, tested against all real content. |
| 20 | Window link | §2: BroadcastChannel; not reliable from `file://`. | BroadcastChannel **and** `postMessage` to the window the leader opened, with every message numbered so repeats are ignored. The display sends only `display-ready` and forwarded keys (→ ← Space R B). | The offline file is opened from disk, where BroadcastChannel is unreliable. Forwarding keys means the leader can keep driving after clicking the projector window to go full screen. |
| 21 | Deep links | §5: every module has its own URL hash. | `#/lead/<meeting>/<step>?short=on`, `#/module/<id>`, `#/modules`, `#/display`. Steps count from 1. Later: `#/game/<id>`, `#/battle/<id>/phase/<n>`. | Works on GitHub Pages and from a file; a leader can text "step 3". |
| 22 | Discussion answers | Not covered. | Discussion questions and their answers stay in the leader view. The leader reads them aloud; they never go to the projector. Questions meant for the screen are written as prompts. | Most discussion answers are leader prompts ("let them argue"), not answer keys. |
| 23 | Schedule indicator | §7.1: a running "behind or ahead" indicator. | Drift counts only steps that were timed: each earlier timed step adds (used − planned), and the current step adds its overrun once past its time. | Starting the clock partway through a meeting shouldn't read as "20 minutes ahead". |
| 24 | Timer hand-off | Not covered. | Moving to another step while the clock runs pauses that step's timer and starts the next one. Each step keeps its own time, so jumping back never loses it. Position, toggles and timers are saved in localStorage; reveal and blank aren't, so after a reload the answer is hidden. | Fewer key presses mid-meeting; a reload can't put an answer on screen. |
| 25 | Teach-back card draw | §7.1: draw a random card from the session's facts. | Deferred to Phase 2, with the tracker. Phase 1 runs teach-back as a normal module page. | It's part of tracking who can explain what. |
| 26 | Offline build | Phase 0 build refused files with `import`; Phase 7 was to fix it. | `scripts/lib/bundle-modules.js` joins the modules now. It supports only named imports and `export function/const/let/class`, and fails clearly on anything else. | The app is split into modules in Phase 1, and the offline file has to keep working. |
| 27 | Unverified facts on screen | Not covered. | The check warns when a prompt or answer key on the projector rests on a `needsVerification` fact. | So a leader sees it before the meeting, not on the projector. |
| 28 | Dead source links in the leader guide | The guide cites an NPS Arlington page, the National Archives Foundation, Grand Forks AFB and USO. | The NPS and Archives Foundation links return 404, and Grand Forks and USO refuse automated checks (403). Those facts cite arlingtoncemetery.mil, govinfo, Wikipedia and OPM instead. | Every fact needs a source that can be checked today. |
